## 阅读源码：SessionStorage 的真实启发

研读了 [pi](https://github.com/earendil-works/pi)，从一开始抓不住重点，到关注 pi-agent-core，再去理解 `interface SessionStorage`。

**我以为它是 JAVA 的继承——错了。** `interface SessionStorage` 是 TypeScript 的 interface / Protocol 形态，是依赖倒置、接口即协议，不是继承。它更准确的叫法是**"边界反腐蚀层"**：上层（agent / runner）只认 SessionStorage 这套抽象概念，不认具体的 JSON / SQLite / 数据库实现；底层换实现，上层零改动。

**这个启发真正落地的位置，不是 SessionStore，而是 `message.py` + `serialization.py`**。07-31 的 `0c1e15c 引入领域消息类型化和边界序列化`：

- 领域层（`message.py`）只认领域类型 `Message` 联合，不认 wire dict；
- 边界层（`serialization.py`）唯一认识 wire，把供应商差异（GLM 的 `reasoning_content`、嵌套 `tool_calls.function`）挡在门外；
- runner / state 一概不 import wire 形状。

**SessionStore 反而是降维版**——只有 `create / load / save / delete / list` 五条整体读写，没有事件日志、没有会话分支、没有 checkpoint marker。降维的原因：项目其他部分不复杂。这条 spec 自己论证过（500 轮会话约几百 KB，分表门槛在百万行 / GB 级），整体读写 JSON 文件就是当前规模下的正确选择。

但要警惕：升级 SessionStore 的触发点不是"变复杂"，是"出现第二个真相源"。消息流一旦要压缩、要分支、要做 RAG 检索，整体读写就会变成反模式——为压缩单独再开文件、再做指针。本周的 compaction spec 拆 `index.json` + `summary.json`，正是这个判断的代价。

所以这件事的教训是：**抽象纪律学到手，能力层（事件日志 / 分支 / checkpoint）不一定都学到**。当前 SessionStore 是降维版，升级触发点是"出现第二个真相源"，不是"变复杂"。

## 遇到的难点

compaction spec 里躺着两面承重墙 + 4 颗未拧的螺丝 + 1 个待验事实。下面按心智消耗大小排：

### 难点 1：压缩设计在动手之前就爆发了认知债

compaction spec 已设计但**还没实现**。本周最大的难点不是"不会做"，是"动手之前就意识到：这件事有 4 颗螺丝 + 2 面承重墙没结"，且这些**我自己结不掉**——必须和 AI 一起论证。

详细论证见 [compaction spec](../specs/compaction.md)。本总结只点几条关键决策：
- **缓存友好放置**：摘要紧跟 system 作为稳定前缀——和滑动窗口每轮前缀都变正好相反，**压缩反而比窗口更省缓存**。
- **边界标记 = message_id，且位置即边界**：在 append-only 的前提下，`index.json` 里追加一条 SummaryMessage 作为标记。**和 pi 存 `firstKeptEntryId` 相反**——这个判断我目前**没能力证伪**，要实现完用真机验证。
- **递归摘要的承重墙 bug**：第二次摘要时，如果输入只含"近期消息"而不含上次摘要正文，"只取最后一个摘要"这条规则就会**静默丢数据**——msg 1..50 的信息彻底消失。两条规则必须捆在一起写。

这难点**没结**。下周继续。

### 难点 2：SSE 工具分片调试

`ab7a532 07-25 修复 SSE 对话思考面板折叠 bug`——具体卡点是：流结束后自动将 reasoning 转为 answer；处理模型把回答放在 `reasoning_content` 的情况；添加工具调用时的思考折叠逻辑。

体感上像"一开始不熟"，但实际节奏是 07-23 动手第一天就撞上了。一周内趟过。

### 难点 3：前 4 天没一行测试

不是"该不该写测试"难，是"当时根本没想到要写"。pytest 引入是 07-27 周一才发生的（`72760e4`）。前 4 天 12 个 commit 都是纯写不测的节奏。

后果：没有反馈环时，无法区分"机制对"和"机制看着对"。compaction 设计里"位置即边界 vs pi 存 firstKeptEntryId"这个判断，目前就属于"机制看着对"——因为还没实现、没真机验证。

## 学习的知识点

### 1. 上下文压缩的猜想（未结）

**机制是我提的，名字是 AI 给的**——event log + checkpoint marker 这套说法，是 AI 告诉我工业界叫这个名字的，我自己一开始只能描述成"在消息流里插一条标记"。WAL、Kafka offset commit 同形状，是 AI 给的类比。

这个猜想**不一定对**。详见 compaction spec 的"螺丝"和"承重墙"——比如"位置即边界 vs 显式 id"就是我**和 pi 相反**的一个判断，必须在实现后用真机验证。

### 2. TDD：第 5 天才补上反馈环

过去开发一直没采用过的方式。7-27 引入 pytest 骨架后，commit 节奏变了。但**前 4 天的 12 个 commit 没一行测试**——所以"用 TDD 提升代码质量"在这个项目里目前**只是体感，不是事实**。具体哪个测试第一次是先写测试后写实现，下周再翻 git。

### 3. 协议设计的体会更深了一层

SessionStorage 的启发**真正落地**在 07-31 的消息类型化 + 边界转换上（`0c1e15c`），不是 SessionStore。这件事在本周总结前一节已经写过，但有一层值得单拎出来：

**我学到了"用接口切分层、用边界挡供应商"这套抽象纪律，但没学到事件日志 / 分支 / checkpoint 这些能力层。** 区分这两件事很重要——前者是"怎么学"，后者是"学了哪些具体形状"。前者可以迁移，后者要按场景学。

### 4. 加深了基础知识认知

这周的几个具体证据：
- 机制是我提的、名字是 AI 给的——说明我**能想出机制**，但**没受过术语训练**。
- AI 重写 SSE、我修折叠 bug——说明我**有手感调产品行为**，但**写不出协议主干**。
- 启发是抽象纪律不是具体设计——说明我**学到了怎么学**，但**没学到工业界现成的形状**。

三件事拼在一起，是"更在意基础"具体指什么：要补的不是"再写一次 SSE"，而是**术语 / 协议主干 / 工业界现成形状**这三类基础。
