# 上下文压缩（Compaction）设计 Spec

> **状态**：设计讨论中，边界标记方案已成型，**还剩 3 颗螺丝没拧**（见文末「明天继续」）。
> **前置**：滑动窗口已完成（`src/agent/context.py` 的 `window_for_api`，非破坏性、配对安全）。
> **进度**：2026-07-30 公司起草 → 07-31 晚上与「架构师」对答，定下边界标记、砍掉冗余设计、发现一处承重墙 bug。

## 背景与问题

- 上下文每轮**全量重发**，累计成本随轮数**平方增长**。
- 第一刀"滑动窗口"已落地，但它会**遗忘**：旧轮次直接滑出窗口，agent 丢失早期关键信息。
  - 已亲测：长会话里先告诉它"我叫小明、预算 5000"，窗口滑掉后问它，**答不上 / 瞎编**。
- **第二刀目标**：把"丢"换成"**浓缩地记着**"——旧轮次压缩成一段摘要，上下文照样被摁住，但要命的信息活在摘要里。

## 目标形状

```
[ system ]  +  [ 旧轮次的摘要 ]  +  [ 近期若干轮 · 逐字保留 ]
   地基          浓缩的"记忆"           热乎的、要精确的细节
```

---

## 已定的设计决策

### 1. 缓存友好放置（本设计的关键）

- 摘要**紧跟 system**，作为**稳定前缀**；近期对话追加在**尾部**（易变）。
- 两次重摘之间，`[system + 摘要]` **冻结** → 缓存命中；只有重摘那一下前缀才变。
- **重摘越不勤，缓存越稳**。
- 对比滑动窗口：窗口每轮从 system 后面滑掉旧轮，前缀每轮都变、缓存每轮都死。**压缩反而比窗口更省缓存**——这是"压缩 vs 缓存"张力的两全解。

### 2. 触发与阈值

- **环境变量 `CONTEXT_WINDOW`** 表示模型上下文大小（`100k` / `1M` 等）——预算**模型感知**，不写死。
- **阈值 25%**：上下文超过窗口的 25% 即触发摘要。
- **安全阀**：若摘要后仍超 25%（信息太密、压不进去），把阈值升到 **50%**，避免过度压缩导致失真。
- ⚠️ 单位注意：`estimate_context_tokens` 数的是**字符**，`CONTEXT_WINDOW` 是 **token**，二者粗对齐。学习够用；真要精确，日后换真 tokenizer。

### 3. 存储：append-only，不是 immutable ⚠️ 措辞已修正

旧措辞是"`index.json` **不动**"，这句和后面的设计打架了（Summary 标记要往里加）。精确的说法是：

| 概念 | 含义 | 本设计 |
|---|---|---|
| **immutable** | 一个字都不能加 | ❌ 不是这个 |
| **append-only** | 只准往后追加，**已写入的永不改写 / 删除** | ✅ 是这个 |

append-only 才是事件日志的正确性保证，而且比 immutable 更有用（否则日志没法长）。

**这条是往后所有操作的合法性判据**：以后拿不准"这么改行不行"，就问一句——**它有没有改写已经写下去的东西？**

- **`index.json`**：逐字全史 + Summary 标记，**append-only**（原始对话真相）。
- **`summary.json`**：摘要正文（摘出来的"记忆"本身）。
- 保留原文 = 为将来留口子：让"摘要模型"回查原文、动态精修摘要（**分层 / 自适应摘要**的高级形态）。

### 4. 边界标记 = message_id ✅（本轮定案）

runner 拼 `[system + 摘要 + 近期]` 时，靠 **message_id** 而非下标 / 时间戳来区分"已摘要 vs 逐字近期"。

**为什么不是下标**（⚠️ 原来的理由是错的，已换）：

- ❌ 错误理由："摘要后下标会变" —— 在 append-only 前提下**下标恰恰是稳定的**，只往后加，第 3 条永远是第 3 条。这个理由站不住。
- ✅ 真理由 1：**下标是"位置"，id 是"身份"**。位置耦合容器，只在"那一个列表、那一种顺序"下有意义；一旦出现第二个列表（窗口后的视图、多来源合并、将来的分支对话），下标立刻失效。id 走到哪儿都是它自己。
- ✅ 真理由 2：**下标是隐式契约**。`summary.json` 里躺着 `[0,1,2,5]`，靠"读的人知道这是 index.json 的下标"才成立——这个约定不在数据里，在人脑里，错了不报错、只静默指向错的消息。uuid 至少对不上就是对不上。

**为什么时间戳不参与判定**：

- 两个判据 = **两个真相源**，迟早不一致，那时不知该信谁。id 已经唯一，时间戳只增歧义、不增能力。
- 它作为**元数据**（人工排查、按时间圈范围）有价值；作为**判据**是负债。

### 5. Summary 标记落在 index.json 里 ✅（本轮定案）

不在 `summary.json` 里存边界 id，而是往 `index.json` **追加一条 SummaryMessage 类型的消息**作为标记：

```
[system][msg 1..50][SummaryMessage][msg 51..100]
                    ↑ 它的位置本身就是边界
```

**为什么这个更强**：边界不再是"指向别处的引用"，它**就在原地**。引用会失效，位置不会。

**这有个工业界的名字**：event log + checkpoint marker —— 数据库的 WAL、Kafka 的 offset commit 都是这个形状。

配套规则：

- SummaryMessage **只做标记**，不 wire 到 API（`message_to_api` 不发它）。
- 有新摘要时，**旧标记不删除**（append-only），runner **只取最后一个**为准。
  - ⚠️ 这条规则单独不成立，必须配一个约束 —— 见下面的「🔴 承重墙 A」。

### 5.1 分层：log + content store ✅（本轮定案，分对了）

| 文件 | 职责 | 归谁管 |
|---|---|---|
| `index.json` | **顺序 + 边界**（日志数据库） | `SessionStore` |
| `summary.json` | **内容**，key-value：`{message_id: 摘要正文}` | `SessionStore` 新增 summary 模块 |
| 视图组装 | 把两者合成 `[system + 摘要 + 近期]` | `AgentState`（领域层） |

**key-value 优于数组的真实原因**（不只是"查得快"）：

| | key-value | 数组 |
|---|---|---|
| 查一段摘要 | O(1) | 得遍历 |
| 顺序信息 | 没有 —— **但不需要**，index.json 已经有序 | 有，**是冗余的第二份顺序** |
| 拆分 | 天然可拆（按 key 分桶） | 拆了就乱序 |

**关键**：顺序留在 index.json、内容放进 summary.json，**两边职责零重叠**。这是 log + content store 的标准分层（git 的 object model、数据库 WAL + 数据页，同形状）。


### 6. 摘要以 SystemMessage 形式进上下文 ✅（结论对，理由已修正）

- 与「摘要紧跟 system 作为稳定前缀」自洽。
- 避开了用 `UserMessage` 的坑：会和 `window_for_api` 的轮边界（以 UserMessage 切轮）打架。

**⚠️ 理由修正：模型里没有"role 加权"这回事。** role 不是乘在注意力上的系数，它就是一段特殊格式的文本标记，模型在后训练时学会了对它的**惯例反应**：

| role | 模型学到的惯例 |
|---|---|
| `system` | 持续生效的设定 / 背景，**不是要我回答的东西** |
| `user` | 对方刚说的话，**我要回应它** |
| `assistant` | 我自己说过的话，我该保持一致 |

所以真理由是**惯例**：摘要放 user 里，模型可能真去"回答"这段摘要；放 assistant 里，模型会以为这些是它自己说的（有框架真这么干，副作用是对没说过的内容过度自信）；放 system 里，模型理解为"背景资料"——这才是要的。

> 💡 理由错了很危险：按"加权"理论会推出"重要信息全塞 system 就更受重视"这种错误结论；按"惯例"理论才会正确推出"system 装设定、user 装诉求"。

### 7. 新能力 `summarize_messages(messages, client) -> str`

- 这是**第一次"用 LLM 管 LLM 自己的记忆"**——模型不再回答用户，转而替 agent 压缩记忆。这个范式（LLM-as-memory-manager）往后摘要 / 长期记忆 / 子代理都会复用。
- **摘要 prompt 工程**：叮嘱模型"保住关键事实 / 用户偏好 / 未决事项，扔掉寒暄与冗余"。prompt 质量直接决定摘要质量。

### 8. 分层职责

- **`AgentState`**：领域层，负责在 build 视图时把 index + summary 合成 `[system + 摘要 + 近期]`。
- **`SessionStore`**：持久化层，只做 `index.json` / `summary.json` 的存取，新增 summary 管理模块。

## ❌ 已砍掉

### 1. "会话目录下再加一个事件记录文件"

- **它已经存在了，就叫 `index.json`**：append-only、按时间顺序、记录每条消息 —— 这就是事件日志的定义。
- 再加一个 = **第二个真相源** = 迟早漂移 = 不知道信谁。
- 📌 **元技能**：需求一复杂，本能反应是"再加个文件 / 再加张表"。正确的反应是先问：**我要记的那件事，现有的哪个东西已经能推导出来？** 推导得出来就别加。

### 2. summary.json / index.json 的「分库分表」

用砍第 1 条的同一把尺子量，量不过去：

1. **现在多大？** `storage/sessions/` 目前是空的。500 轮会话约几百 KB。分表门槛通常在**百万行 / GB 级**。
2. **"文件过大"是多大？** 说不出具体数字，就不是工程判断，是焦虑。
3. **分库分表是数据库术语**，对 JSON 文件对应的只是"多开几个文件"——这个类比迁移过来未必成立。

**但好消息是这本来就是你设计的功劳**：key-value 结构**天生可拆**（按 key 前缀分桶即可）。所以正解是——

> **形状留好，实现不做。** "将来能拆"这个性质已经免费拿到了，现在动手拆等于把免费的东西花钱买一遍。

📌 **元技能**：区分「**支持**未来扩展」和「**实现**未来扩展」。前者是好设计，几乎不花钱；后者是 YAGNI，当场就要付复杂度。key-value 已经做到前者，别越界做后者。

## 🔴 承重墙 A：「只取最后一个摘要」有静默丢数据的 bug

第二次触发摘要时，index.json 长这样：

```
[system][msg 1..50][Summary-A][msg 51..100]  ← 现在要摘第二次
```

**问：第二次摘要，喂给模型的输入是什么？**

| 输入 | 后果 |
|---|---|
| 只有 `msg 51..100` | 产出 Summary-B。按"只取最后一个"，runner 只用 B —— **msg 1..50 的信息彻底消失**（既不在近期里，也不在 B 里）。验收测试会失败，而且失败得很晚、很隐蔽。 |
| `Summary-A 正文 + msg 51..100` | Summary-B 包含全部历史，"只取最后一个"才成立。 |

**结论**：「只取最后一个摘要」**不是能单独成立的规则，而是一个约束** ——
> **每次摘要的输入必须包含上一次的摘要正文。**

这两条必须**捆在一起**写进 spec，否则后来改动其中一条，另一条就悄悄崩了。

**已知代价**（这叫 rolling / 递归摘要，是标准做法）：信息每摘一次损失一点，**摘 10 次后最早的信息已被压成渣**。这是压缩的固有代价，不是 bug，但要心里有数。

## 🔴 承重墙 B：两个文件 = 写入顺序问题（拆分层的代价）

把数据拆成 `index.json` + `summary.json`，**这一拆就引入了新问题**：一次摘要要写两个地方。

```
① summary.json 写入摘要正文（内容）
② index.json 追加 SummaryMessage（指针）
```

**如果在 ① 和 ② 之间断电 / 崩溃 / Ctrl+C 呢？**

| 顺序 | 崩了会怎样 |
|---|---|
| **先内容 ①，后指针 ②** | summary.json 多一条**没人指向的孤儿**。下次加载：完全正常，就当没摘过，重摘一次。**可恢复** ✅ |
| 先指针 ②，后内容 ① | index.json 有指针指向**不存在的摘要**。下次加载：解引用失败，**会话直接打不开** 💀 |

> **规则：内容先写，指针后写。指针的出现 = 提交（commit）。**

不是编的：git 先写 blob 对象、最后才更新 ref；WAL 同理。**一旦选择"拆成两个文件"，就必须处理这个问题** —— 这是分层的代价，不是免费午餐。

❓ 待想：孤儿数据要不要清理？（提示：git 管这叫 gc，而且它**不属于** append-only 保证的一部分。）

## ⏳ 明天继续：还剩 4 颗螺丝 + 1 个事实待验

### 🔩 螺丝 1｜SummaryMessage 到底要不要 start_id / end_id？（**同一个坑第三次**）

已经论证过两遍：**messages 有序 + 标记的位置就是边界**。所以

- `end` = 标记**前面**那条 → 位置已给
- `start` = 上一个标记**后面**那条 → 位置已给

存进去 = **第二份边界数据**。这正是 §4 砍掉时间戳的同一个理由。

**用这个手法逼自己表态**（通用技巧，记下来）：

> 给两份数据**制造一次冲突**，问自己信哪个。
> 如果某天标记的**位置**和它声明的 `start/end` 对不上（bug / 并发写 / 手改过文件），**你信哪个？**

| 回答 | 结论 |
|---|---|
| 答不上来 | 这份数据不该存在 → 删 |
| "信位置" | `start/end` 是死字段 → 删 |
| "信 start/end" | 那就不该用位置当边界 → **§5 整个推翻重来** |

**三选一，必须选一个。**

### 🔩 螺丝 2｜summary.json 的 key 是"哪一条"消息的 id？

- (a) **被摘范围最后一条**的 id → SummaryMessage 必须存着它，才知道查哪个 key。
- (b) **SummaryMessage 自己**的 id → 标记**不需要任何额外字段**：身份即钥匙，位置即边界。

选 (b) 的话，`SummaryMessage` 的定义会短到有点好笑。**这是不是你要的？自己判。**（注意它和螺丝 1 是同一个决策的两面。）

### 🔩 螺丝 3｜递归摘要那条约束，认不认？

- ❓ 承认「每次摘要输入必须包含上次摘要正文」（承重墙 A）吗？
- ❓ 如果认，它写在哪一步的代码里？触发逻辑里，还是 `summarize_messages` 的入参组装里？

### 🔩 螺丝 4｜摘要切分会不会切断 tool 配对？（欠了两轮了）

- ❓ 发给 API 会怎样？`_validate_invariants` 会不会当场抛？
- 💡 提示：`window_for_api` 已解过同一个陷阱（"以 UserMessage 为轮边界整段切 → 配对自动安全"）。**同样的解法能不能直接搬？**

### 🔬 事实待验｜API 允许几条 system？

目标形状是 `[system][摘要 system][近期...]` —— **列表里有两条 system**。

- ❓ 接的这个 OpenAI 兼容 API，**允许多条 system 吗**？会不会只认第一条、或直接报错？
- ⚠️ **不要猜，去查文档或直接发一个请求试。**
- 📌 **元技能**：设计里凡是依赖"外部系统行为"的地方都是**事实问题**，事实问题只能**验证**，不能推理。
- ❓ 追问：**如果只允许一条 system，设计要怎么改？** 想到答案会发现，那个改法可能反而对 §1 的缓存前缀更友好。

## 实现子步骤

1. ~~定边界标记~~ ✅ 已定：`message_id` + index.json 里的 Summary 标记。
2. **先答完上面 3 颗螺丝 + 验证 system 条数**（不答完写到第 5 步会撞墙）。
3. 给 `Message` 加 `id` + 新增 Summary 类型；`serialization.py` 两侧适配（`to_api` 不发 id / 不发 Summary 标记；`from_api` 兜住没有 id 的老消息）。
4. `summarize_messages` + 摘要 prompt（配 **FakeClient** 即可测，不烧真 token）。
5. 摘要的存 / 取（`summary.json` + Summary 标记）。
6. 组装 `[system + 摘要 + 近期]` + 阈值触发 / 升级逻辑（含递归摘要约束）。
7. 接入 runner（配合 / 替换窗口）+ 持久化。
8. **真机验证**：长会话恢复后，早期关键信息应活在摘要里——再问"我叫什么 / 预算多少"，**应答得上**。
